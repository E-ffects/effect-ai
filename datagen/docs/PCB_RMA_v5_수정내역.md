# PCB RMA v5 · 수정 내역 (재발 사건, 헛신호, 지저분한 고객 문장)

- 작성: 2026-11-18
- 기준: v4 (`PCB_RMA_v4_수정내역.md`). 테이블·컬럼 구조는 v4와 같고 `claim_text_variant` 테이블 하나만 늘었다.
- 설계: `PCB_RMA_v5_설계.md`

## 왜 바꿨나
v4로 원인분석 에이전트를 평가해 보니 데이터가 너무 깨끗해서 숫자가 실제보다 좋게 나왔다.
- 사건성 원인 19개 중 재발은 드릴 비트(P01 → P01R) 하나뿐이었다.
- 공정 이상 신호가 대부분 진짜 원인 공정에만 있었다.
- 고객 문장이 정형화돼 분류 LLM이 표본 100%였다.

v5는 이 세 가지를 보강한 **시험용 데이터**다. 숫자가 떨어지는 게 정상이다.

## 바뀐 것
### 1. 재발 사건 4개 (반품 +610건, 10,000 → 10,610)
| 재발 조사 | 다시 연 조사 | 원인 | 재발 이유 | 장비 | 반품 |
|---|---|---|---|---|---:|
| INV-25-0020 (P04R) | INV-25-0009 | 디스미어 부족 | 교체 기준을 DSM-02에만 적용(수평 전개 누락) | DSM-01 | 180 |
| INV-25-0022 (P05R) | INV-25-0003 | 홀 도금 두께 부족 | 정류기 모듈만 교체, 예방 보전 주기 미설정 | PLT-03 | 150 |
| INV-25-0024 (P12R) | INV-25-0012 | 내층 과에칭 | 점검 주기를 기준서에만 반영, 현장 미준수 | ILE-02 | 160 |
| INV-25-0026 (P09R) | INV-25-0011 | PSR 잉크 점도 이탈 (자재) | 공급사 시정조치 후에도 성적서 의존 수입검사 유지 | 같은 공급사 다른 Lot | 120 |

- 원래 조사는 `REOPENED_LINKED`, 재발 조사는 `reopened_from`으로 잇는다(P01R과 같다).
- 원래 대책(`corrective_action`, OCCURRENCE)에 재발 이유가 문구로 남고, 재발 조사에는 수평 전개 대책(HORIZONTAL)이 붙는다.
- 재발 판정(`recurrence_review`)의 `RECURRENCE` 756건. 재발 관리 화면과 대책 효과율에 데이터가 생긴다.
- 단발 반품 수는 그대로다(전체 반품 수를 610건 늘렸다).

### 3. 지저분한 고객 문장 (10월 이후 3,531건 중 457건, 12.9%)
| 유형 | 건수 | 예 |
|---|---:|---|
| 맞춤법 틀림·축약 (`typo`) | 152 | "간헐적으로 단선되요" |
| 영어·약어 (`english`) | 118 | "PCB 표면이 볼록하게", "short", "delam" |
| 돌려 말하기 (`paraphrase`) | 103 | "BGA를 떼어 보니 패드 표면째로 분리되고 면이 검게 보입니다" |
| 증상 두 개 (`two_symptoms`) | 59 | 주 증상 뒤 "몇 장은 PSR 가장자리가 살짝 들떠 있습니다" |
| 더 모호하게 (`vague`, 정보 부족만) | 25 | "육안상으로는 특이점이 없습니다" |

- 정답(`symptom_assessment.intake_label`)은 바꾸지 않았다. 근거 구절(`evidence_spans_json`)은 바뀐 문장에 맞췄다.
- **새 테이블 `claim_text_variant`**: `rma_id`, `variant`, `original_raw_text`, `original_evidence_spans_json`. 평가 때 깨끗한 문장과 나눠 볼 때 쓴다(서비스 입력으로 쓰지 않는다).

## 재현
```
PYTHONHASHSEED=0 ./run_all.sh <출력 폴더>
```
`generate_v30` → `finalize_v30` → `patch_v31` → `reconcile_v31` → `patch_v3` → `patch_v3_text` → `patch_v3_severity` → **`patch_v5_noise`** → **`patch_v5_text`** → `finalize_v3` → `patch_v4_loss` → `patch_v4_terms` → `slim_v3`

- 생성기 일부가 파이썬 `hash()`로 난수를 만들어 실행마다 결과가 달랐다. `PYTHONHASHSEED=0`으로 고정했다. 그래서 **v4는 그대로 재현되지 않는다**(v4 원본은 보관). v4 설정으로 다시 만들면 행 내용이 달라진다.
- 생성기 수정: P01R 전용 처리 4곳을 `recurrence_of`를 쓰는 일반 처리로 바꿨다. 원래 사건의 대책 문구는 `occ_ca`, 재발 대책은 `recur_ca`로 설정한다.
- 손실 계산(`patch_v4_loss`): 공장 보류 후 선별(`HOLD_THEN_<선별 종류>`)은 그 선별 단가를 쓴다.

## 검증
- 각 단계의 자체 검사 통과, `pragma integrity_check` ok, 외래 키 위반 0, 기준 시점 이후 데이터 0
- 테이블 46개(v4 45 + `claim_text_variant`), 뷰 10개

## 에이전트 평가 (2025-10-01 이후, 알려진 원인 2,537건, LLM 없이)
| 그룹 | B 소분류 투표 원인@1 | **C 원인분석 원인@1** | C 장비@1 |
|---|---:|---:|---:|
| 전체 (v4: C 85.5%) | 52.7% | **78.2%** | 89.7% |
| 다른 사건 같은 원인 | 55.6% | 63.5% | - |
| 헛신호가 걸친 Lot (898건) | 47.9% | 80.2% | 91.3% |
| 재발 P04R 다른 장비·신호 강함 | 52.2% | 90.6% | 90.6% |
| 재발 P05R 같은 장비·신호 중간 | 0.0% | 78.7% | 78.7% |
| 재발 P12R 다른 장비·신호 약함 | 98.1% | 70.0% | 98.1% |
| **재발 P09R 자재·다른 Lot** | 97.5% | **12.5%** | - |

- 헛신호에는 끌려가지 않았다(헛신호 Lot 80.2% ≥ 전체 78.2%).
- 평가 중 발견: 이미 원인이 승인된 사건에 들어온 반품은 접수 시각에 원인이 붙어 분석 시작 전부터 "과거 사례"가 된다(v4 117건, v5 209건). 에이전트가 분석 대상 자신을 과거 사례에서 빼도록 고쳤다(effect-ai `AsOfStore(subject=...)`). 숫자 영향은 0.1%p 이하.
- **자재 재발(P09R)이 깨졌다.** 과거 사례의 문제 자재 Lot과 이 Lot의 자재가 다르면 0.8 감점하는 규칙 때문이다. 같은 공급사·같은 자재 종류면 감점을 줄이는 식의 수정이 필요하다. 튜닝 기간(7~9월)에는 자재 재발이 없으므로, 고칠 때 평가 기간 결과로 맞추지 않도록 주의한다.
